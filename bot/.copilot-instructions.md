## 🎯 Arquitectura y Principios

Este proyecto sigue una **arquitectura modular estricta**. Antes de escribir código, SIEMPRE consulta `/ARCHITECTURE.md` para entender dónde debe ir cada funcionalidad.

### 📋 Reglas de Modularidad OBLIGATORIAS

#### 1. **Jerarquía de Dependencias - NO VIOLAR**
```
config/ → types/ → utils/ → services/ → controllers/ → routes/
```
- Los módulos de arriba NO pueden importar los de abajo
- Cada nivel solo puede importar niveles anteriores

#### 2. **Clasificación de Funcionalidad**

**Utils** (funciones puras):
- ✅ Sin estado interno
- ✅ Misma entrada = misma salida
- ✅ Sin efectos secundarios
- ❌ NO gestión de archivos directa
- ❌ NO llamadas a APIs sin parámetros
- ❌ NO estado persistente

**Services** (clases con estado):
- ✅ Gestión de estado interno
- ✅ Operaciones con sistemas externos
- ✅ Gestión de recursos (archivos, conexiones)
- ✅ Lógica compleja multi-paso

#### 3. **Ubicación por Funcionalidad**

| Si es... | Va en... | Ejemplo |
|----------|----------|---------|
| Función pura, sin efectos secundarios | `utils/` | `formatPhoneNumber()` |
| Clase con estado interno | `services/` | `DirectoryManagerService` |
| Orquestación de services | `controllers/` | `MessageController` |
| Endpoint HTTP | `routes/` | `/api/send-message` |
| Configuración/constantes | `config/` | `BOT_PORT` |
| Definición de tipos | `types/` | `MessageFormat` |

### 🚫 Anti-Patrones - NO HACER

1. **NO centralizar todo en utils**
   ```typescript
   // ❌ MAL - whatsAppUtils con QR, API endpoints, file management
   // ✅ BIEN - whatsAppUtils solo para lógica de WhatsApp pura
   ```

2. **NO violar jerarquía de dependencias**
   ```typescript
   // ❌ MAL
   import { MessageController } from '../controllers/'; // en utils
   
   // ✅ BIEN
   import { formatMessage } from '../utils/'; // en controllers
   ```

3. **NO mezclar responsabilidades**
   ```typescript
   // ❌ MAL - función que hace muchas cosas
   function initializeEverything() {
     createDirectories();
     startWhatsApp();
     setupAPI();
     configureDatabase();
   }
   ```

### 🎯 Naming Conventions

- **Utils**: `camelCase` functions → `formatPhoneNumber`
- **Services**: `PascalCase` + `Service` → `MediaMessagingService`
- **Controllers**: `PascalCase` + `Controller` → `MessageController`
- **Types**: `PascalCase` → `MessageFormat`, `BotConfig`

### 📝 Flujo de Desarrollo

1. **Antes de escribir código:**
   - ¿Es función pura? → `utils/`
   - ¿Necesita estado? → `services/`
   - ¿Orquesta services? → `controllers/`
   - ¿Es endpoint? → `routes/`

2. **Al refactorizar:**
   - Identifica violaciones de modularidad
   - Mueve funcionalidad al lugar correcto
   - Actualiza imports en toda la aplicación
   - Mantén la jerarquía de dependencias

3. **Checklist de validación:**

### 🎨 Estilo de Código

```typescript
// ✅ Función pura en utils
export function formatPhoneNumber(phone: string): string {
  return phone.replace(/[^\d]/g, '');
}

// ✅ Service con estado
export class DirectoryManagerService {
  private directories: string[] = [];
  
  public ensureDirectoriesExist(): void {
    // lógica con estado
  }
}

// ✅ Controller orquestando services
export class MessageController {
  constructor(
    private messageService: MessageService,
    private validationService: ValidationService
  ) {}
  
  async sendMessage(data: MessageData): Promise<MessageResult> {
    const validatedData = this.validationService.validate(data);
    return await this.messageService.send(validatedData);
  }
}
```
